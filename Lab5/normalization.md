# Лабораторна робота №5: Нормалізація бази даних

**Тема:** Аналіз функціональних залежностей та нормалізація схеми бази даних "Gaming Social Network".

---

## 1. Аналіз функціональних залежностей

Ми проаналізували основні таблиці нашої схеми (`users`, `posts`, `comments`) на предмет надлишковості даних та аномалій оновлення.

### Таблиця `users`
- **Первинний ключ:** `user_id`
- **ФЗ:** `user_id → nickname, email, password, reg_date`
- **Аналіз:** Усі атрибути залежать виключно від ідентифікатора користувача. Аномалій немає.

### Таблиця `comments`
- **Первинний ключ:** `comment_id`
- **ФЗ:** `comment_id → post_id, user_id, comment_text, created_at`
- **Аналіз:** Текст коментаря та його метадані залежать від ID коментаря. Аномалій немає.

### Таблиця `posts` (Кандидат на оптимізацію)
- **Первинний ключ:** `post_id`
- **Поточні ФЗ:** `post_id → user_id, title, content, created_at`
- **Проблема:** У соціальній мережі пости мають різні типи (Огляди, Гайди, Новини). Зберігання цієї інформації у вигляді текстового поля `category` (VARCHAR) призведе до:
    1.  **Надлишковості:** Рядок "Review" дублюватиметься тисячі разів.
    2.  **Аномалій оновлення:** Зміна назви категорії вимагатиме оновлення всіх рядків таблиці.
    3.  **Помилок введення:** Різне написання ("Guide", "guide") ускладнить фільтрацію.

---

## 2. Перевірка нормальних форм

### Перша нормальна форма (1NF)
**Вимога:** Атомарність атрибутів, відсутність груп, що повторюються.
- **Статус:** Виконується.
- **Обґрунтування:** Ми не зберігаємо списки (наприклад, теги) в одній комірці. Для зв'язку багато-до-багатьох використовується проміжна таблиця `post_tags`.

### Друга нормальна форма (2NF)
**Вимога:** Відсутність часткових залежностей (неключові атрибути залежать від усього складеного ключа).
- **Статус:** Виконується.
- **Обґрунтування:** У таблицях зі складеними ключами (наприклад, `post_tags`) немає атрибутів, які залежали б лише від частини ключа (наприклад, опис тегу не зберігається в таблиці зв'язку).

### Третя нормальна форма (3NF)
**Вимога:** Відсутність транзитивних залежностей (неключовий атрибут не повинен залежати від іншого неключового атрибута).
- **Рішення:** Для реалізації категорій постів ми створюємо окрему сутність-довідник `post_types`. Це дозволяє уникнути транзитивної залежності, яка виникла б при додаванні полів `type_name` та `type_desc` безпосередньо в таблицю `posts`.

## 3. Реалізація змін (Refinement)

Ми модифікуємо схему, додаючи таблицю-довідник (Lookup Table) для типів постів.

### SQL-скрипт нормалізації

```sql
-- 1. Створення таблиці-довідника для типів постів
CREATE TABLE post_types (
    type_id SERIAL PRIMARY KEY,
    type_name VARCHAR(50) NOT NULL UNIQUE
);

-- 2. Наповнення довідника даними
INSERT INTO post_types (type_name) VALUES 
('General'),   
('Guide'),     
('Review'),    
('News'),     
('Question'); 

-- 3. Додавання посилання до таблиці posts
ALTER TABLE posts 
ADD COLUMN type_id INT;

-- 4. Оновлення існуючих постів
UPDATE posts 
SET type_id = 1 
WHERE type_id IS NULL;

-- 5. Встановлення обмеження NOT NULL та Foreign Key
ALTER TABLE posts 
ALTER COLUMN type_id SET NOT NULL,
ADD CONSTRAINT fk_post_type 
FOREIGN KEY (type_id) REFERENCES post_types(type_id);
